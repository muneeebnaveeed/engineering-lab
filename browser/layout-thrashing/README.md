> written *while* debugging, not reconstructed afterwards — the messy middle is the point.

## 1. Concept

What mechanism is under test, in one paragraph, in your own words.

## 2. Expected behavior

What should happen if the mechanism works as documented. State it precisely enough to be wrong.

## 3. Failure introduced

The specific change made to break it. Include the diff or the exact code.

## 4. Observation

Which tools were used and what they actually showed — profiler traces, query plans, metrics,
logs, flame graphs. Paste real output, not a summary of it.

## 5. Diagnosis

The reasoning from symptom to cause. Include the hypotheses that turned out to be wrong and how
they were eliminated — that record is worth more later than the correct answer alone.

## 6. Fix

The change that resolved it, and why it works.

## 7. Verification

Evidence the fix held: the same measurement, before and after. Numbers, not impressions.

## 8. Explanation

Explain the whole thing as if to another engineer in under two minutes. If it can't be explained
without rereading the code, the lab is not finished.
